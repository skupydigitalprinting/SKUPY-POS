# Financial containment release, 12 September 2026

## Scope

This is an interim frontend containment/reporting release, not completion of the
atomic-payment, accounting-standard compliance, cancellation or authentication work.
No historical financial records, SQL, grants, accounts or login mode were changed.

- Order and Piutang only acknowledge a verified successful callback. Ambiguous
  results retain amount and tender, show an owner-review warning and block repeat
  attempts in the current hook/page session, including modal close/reopen.
- Scoped installment/correction writes verify returned row identities. Preflight
  checks stop invalid balances, missing links, known unresolved customer summaries,
  unsupported payment methods and overpayments before financial writes.
- FIFO respects the selected book, stops at failure and preserves partial results.
- Paid invoice/debt deletion and cancellation are blocked until an explicit DP
  disposition workflow exists. Outstanding linked receivable cancellation is also
  held for owner review. This does not erase or settle historical balances.
- Order now passes Cash/Transfer/QRIS to the common installment callback.
- Dashboard reconstructs initial tender from cumulative paid minus available
  installment history, counts receipt events once, keeps unrefunded cancelled
  receipts and uses WIB half-open period boundaries. Historical DP is an inference,
  not a proven ledger reconstruction.
- Report queries use verified debt_payments column names and exact-count pagination.
  Missing sources and stale-period results no longer become complete cashflow or
  period-profit totals. Deleted receipts are excluded from active history.

## Remaining Gaps

The eight unchanged exported-schema SQL failures concern receipt date and tender,
cancelled receivables/DP, customer turnover, opening debt receipts, stale reposting
and concurrent payment updates. They are simulated SQL findings, not eight proven
live corrupt transactions. No candidate SQL was applied to hide these failures.

Current legacy browser identity cannot authorize a privileged atomic server RPC.
Cross-cashier atomicity, durable idempotency across reloads and rollback are NOT
provided by these frontend guards. Do not repeat an uncertain payment after reload;
the owner must verify invoice, debt, receipts and actual received funds first.

Next gates: an active owner recovery email and verified account mapping, a complete
database/file backup with isolated restore test, authenticated server operations,
row locks and durable operation receipts, corrected event-ledger posting, legacy
writer cutover, then explicit refund/customer-credit/fee cancellation handling.
Existing profit classification was not certified or comprehensively redesigned.
